# voXY — Design Proposal (v1, approved)

Status: **approved on 2026-10-09**, with the decisions recorded below.
Milestone 1 is implemented against this design. Sections 1–8 keep the
original proposal text. Where the implementation refines the proposal, the
"Implementation notes" section at the end says so.

## Decision record

| # | Decision |
|---|---|
| Q1 | UI: **egui via eframe + egui_dock**. |
| Q2 | Vector: **vello + kurbo + parley + i_overlay**. One `wgpu` version is shared by vello and eframe, recorded in the README. |
| Q3 | OpenFX: **out-of-process sandbox, one helper process per plugin bundle**. |
| Q4 | Determinism: **bit-identical on the same machine and driver; near-identical across GPUs.** Golden tests use a small tolerance. |
| Q5 | Encoders: **hardware first; OpenH264 as the H.264 software fallback; kvazaar for H.265.** LICENSING.md states that patent licensing is the distributor's responsibility. |
| Q6 | Projects: **JSON in a single `.voxy` file with a `<name>.assets/` folder**, plus a `.voxyz` zip for sharing. |
| Q7 | Platforms: **Windows 10+ x64, Ubuntu 22.04+ x64, macOS 12+ (Apple Silicon and Intel).** ARM Windows and ARM Linux are out of scope for now. |
| Color | **Per-project working space.** voXY projects default to linear light. Alight Motion imports default to whichever space the golden tests show matches the reference renders. |
| AM XML | **Lossless XML tree with typed structs on top.** Unedited files are reproduced byte-for-byte. |
| AM ToS | The owner checks the terms before Compat 2a. Only files the owner exports from their own copy are used. |

## 1. Workspace layout

```
voxy/                          (cargo workspace, resolver = "3", edition 2024)
├─ crates/
│  ├─ voxy-core/               document model, time, properties, keyframes,
│  │                           interpolation, commands, undo/redo, evaluation
│  ├─ voxy-vector/             path geometry (kurbo), booleans, strokes/dashes,
│  │                           text layout (parley), scene building for rasterizer
│  ├─ voxy-render/             wgpu compositor, render graph, WGSL shaders,
│  │                           texture pool, frame cache, color pipeline
│  ├─ voxy-media/              FFmpeg decode/encode (dynamic LGPL), audio mixer,
│  │                           cpal output, media clock, waveform peaks
│  ├─ voxy-ofx-sys/            bindgen output for OpenFX headers (checked in)
│  ├─ voxy-ofx-host/           OFX host: discovery, suites, actions, IPC client
│  ├─ voxy-ofx-sandbox/        helper binary that actually loads plugins (bin)
│  ├─ voxy-am-compat/          Alight Motion XML/zip ⇄ typed model ⇄ voxy-core
│  ├─ voxy-ui/                 egui application shell, panels, gizmos, editors
│  └─ voxy-app/                binary → executable `voxy`, display name "voXY"
├─ mappings/am/                data-driven AM mapping tables (TOML)
├─ docs/                       am-format.md, architecture, file-format spec
├─ tests/golden/               reference frames + sample projects (git-LFS)
├─ fuzz/                       cargo-fuzz targets (am-compat parser, .voxy loader)
├─ third_party/openfx/         vendored BSD-3 OpenFX headers (pinned tag)
└─ xtask/                      bindgen regen, coverage report, golden refresh
```

Two crates beyond the brief, both small:
- **`voxy-ofx-sys`** isolates the generated FFI so `voxy-ofx-host` stays readable
  and the `unsafe` surface is in one place. The bindings are generated by
  `cargo xtask bindgen` from the pinned headers and checked in, and CI verifies
  that regenerating them produces no diff.
- **`voxy-ofx-sandbox`** is the out-of-process plugin runner (see §6), if you
  approve that approach.

Dependency direction (no cycles): `core ← vector ← render ← ui ← app`;
`core ← media ← render`; `core ← am-compat`; `core ← ofx-host ← render`.
`voxy-core` has no GPU, FFmpeg or UI dependency, so the model, interpolation,
commands and AM compat can be unit-tested and fuzzed headless.

## 2. Time

```rust
/// Time in *flicks* (1/705_600_000 s). Every common frame rate (23.976, 24, 25,
/// 29.97, 30, 48, 50, 59.94, 60, 120) and audio rate (8k–192k) divides it
/// exactly, so frame ↔ time conversions are integer-exact.
#[derive(Copy, Clone, Eq, Ord, Hash, Serialize, Deserialize)]
pub struct Time(pub i64);

pub struct FrameRate { pub num: u32, pub den: u32 }   // 30000/1001 etc.
```

Interpolation math runs in `f64` on a normalized `t ∈ [0,1]` computed from
integer times, so evaluating a given frame always gives the same value. The time
units AM uses will be handled in its mapping table once the samples show what
they are.

## 3. Document model (`voxy-core`)

### 3.1 Identity and ownership
- Every node gets a stable ID (`LayerId`, `CompId`, `EffectId`, `PropId`, `AssetId`).
  Each ID is a `u64` newtype taken from a per-document counter and serialized
  as-is. IDs never shift on reorder, so undo, selection, the cache and OFX
  instances can all key on them.
- **Copy-on-write snapshots:** each composition and layer sits behind an
  `Arc`, and edits go through `Arc::make_mut`. An edit to one layer copies that
  layer and the path from it to the root; everything else is shared.

```rust
pub struct Document {
    pub meta: ProjectMeta,                 // name, format_version, color settings
    pub assets: Arc<AssetTable>,           // media/fonts/LUTs; relative paths + hashes
    pub comps: Arc<BTreeMap<CompId, Arc<Composition>>>,
    pub root_comp: CompId,
    pub foreign: ForeignData,              // preserved AM data at document level
    next_id: u64,
}

pub struct Composition {
    pub id: CompId,
    pub name: String,
    pub size: UVec2,                       // canvas pixels
    pub frame_rate: FrameRate,
    pub duration: Time,
    pub background: Property,              // animatable color
    pub layers: Vec<Arc<Layer>>,           // index 0 = top of stack
    pub foreign: ForeignData,
}

pub struct Layer {
    pub id: LayerId,
    pub name: String,
    pub kind: LayerKind,
    pub in_point: Time, pub out_point: Time,  // on comp timeline
    pub start_offset: Time,                    // source time at in_point (trim/split)
    pub time_remap: Option<Property>,          // precomps & video
    pub parent: Option<LayerId>,
    pub transform: Transform,                  // anchor, position, scale, rotation, opacity
    pub blend_mode: BlendMode,
    pub matte: Option<TrackMatte>,             // { source: LayerId, mode: Alpha|AlphaInv|Luma|LumaInv }
    pub masks: Vec<Mask>,                      // path: Property(Path), mode, feather, opacity, inverted
    pub effects: Vec<EffectInstance>,
    pub flags: LayerFlags,                     // visible, solo, locked, audio_enabled, …
    pub foreign: ForeignData,
}

pub enum LayerKind {
    Solid    { color: Property },
    Gradient { gradient: Property },
    Image    { asset: AssetId },
    Video    { asset: AssetId, audio: Option<AudioProps> },
    Audio    { asset: AssetId, audio: AudioProps },       // volume, pan (animatable)
    Shape    { shapes: Vec<ShapeItem> },                 // rect/ellipse/polygon/star/path + fill/stroke
    Text     { text: TextDoc, animators: Vec<TextAnimator>, path: Option<TextPathOpts> },
    Group    { children: Vec<Arc<Layer>> },              // in-comp grouping, transforms compose
    Precomp  { comp: CompId },
    Adjustment,                                          // effects apply to the stack below
}
```

`ForeignData` carries anything voXY doesn't model, so an import followed by an
export keeps it (§7).

### 3.2 Properties

Properties use a **dynamic value enum plus a descriptor**. They are not generic
over `T`. OFX parameters, AM effect parameters and built-in effect parameters
all come from data and show up at runtime, and they all need to keyframe, show
in the graph editor, serialize and undo the same way. A generic `Property<T>`
would push trait objects or macro plumbing into every one of those paths.

```rust
pub enum Value {
    Bool(bool), Int(i64), Scalar(f64),
    Vec2(DVec2), Vec3(DVec3),
    Color(LinearRgba),            // f32 linear, straight alpha in the model
    Enum(u32), String(Arc<str>),
    Path(Arc<BezPath>),           // shape/mask path; interpolated vertex-wise
    Gradient(Arc<GradientStops>),
}

pub struct Property {
    pub id: PropId,
    pub desc: Arc<PropertyDesc>,        // shared, static per property type
    pub anim: Animation,
    pub expression: Option<Expr>,       // reserved for later; not in M1–M6
}

pub struct PropertyDesc {
    pub key: Arc<str>,                  // "transform.position", "ofx:<plugin>/<param>"
    pub kind: ValueKind,
    pub default: Value,
    pub range: Option<(f64, f64)>, pub soft_range: Option<(f64, f64)>,
    pub unit: Unit,                     // px, deg, %, s, normalized, …
    pub dimensions: u8,                 // separate-dimension curves in graph editor
    pub animatable: bool,
}

pub enum Animation {
    Static(Value),
    Keyframed(KeyframeTrack),
}

pub struct KeyframeTrack { pub keys: Vec<Keyframe> }  // sorted by time, unique times

pub struct Keyframe {
    pub time: Time,
    pub value: Value,
    pub out_interp: Interp,             // segment from this key to the next
    pub temporal: TemporalEase,         // in/out bezier handles for value-vs-time
    pub spatial: Option<SpatialTangents>, // Vec2/Vec3 only: motion-path handles
    pub flags: KeyFlags,                // roving, continuous, selected-in-UI not stored
}

pub enum Interp { Hold, Linear, Bezier }

/// Value-vs-time easing as a normalized cubic-bezier (x1,y1,x2,y2) per segment,
/// per dimension when dimensions are separated. Presets (ease-in, ease-out,
/// overshoot, …) are named constants that resolve to this form.
/// One handle pair per dimension (1–3).
pub struct TemporalEase { pub out_handle: SmallVec<[DVec2; 3]>, pub in_handle: SmallVec<[DVec2; 3]> }

pub struct SpatialTangents { pub in_tan: DVec3, pub out_tan: DVec3 }
```

Evaluating a property:
1. Find the segment by binary search on `time`.
2. Hold returns the left value. Linear lerps. Bezier solves `x(s)=t` with
   Newton plus bisection fallback (bounded iterations, deterministic) and
   returns `y(s)`.
3. If spatial tangents exist, the position follows a cubic motion path, and
   `y` is used as **arc-length progress** along it through a precomputed LUT,
   so speed follows the graph editor and not the parameterization.
4. Paths interpolate vertex-wise once vertex counts match. Mismatched counts are
   resampled by a deterministic rule (documented, tested).

Interpolation gets exhaustive unit tests plus property-based tests (`proptest`):
the curve passes through every key, bezier easing is monotone in x, hold is
exact, and spatial arc-length progress is monotone.

### 3.3 Commands and undo/redo

Undo stores **snapshots, not inverse operations**. Every edit is a `Command`
that mutates a `Document`. Before it runs, the undo stack stores the previous
`Arc<Document>`, which is cheap because of copy-on-write sharing. Undo swaps
the old snapshot back in. That rules out the whole class of "the inverse
operation was wrong" bugs, and it gives "undo for every operation" without
writing an inverse for each one.

```rust
pub trait Command: Send + 'static {
    fn label(&self) -> Cow<'static, str>;          // "Move Keyframes", for Edit menu
    fn apply(&self, doc: &mut Document) -> Result<(), CommandError>;
    /// Coalescing for continuous edits (gizmo drags, slider scrubs): if Some,
    /// consecutive commands with the same key inside one interaction collapse
    /// into a single undo step.
    fn merge_key(&self) -> Option<MergeKey> { None }
}

pub struct History {
    current: Arc<Document>,
    undo: Vec<(Arc<Document>, Cow<'static, str>)>,
    redo: Vec<(Arc<Document>, Cow<'static, str>)>,
    open_txn: Option<Transaction>,   // groups many commands into one step
    limit_bytes: usize,              // approximate, trims oldest
}
```

- `History::execute(cmd)` clones the `Arc` and runs `apply` on the copy. On
  success it publishes the new snapshot, and on error it leaves the document
  unchanged. Every edit is therefore atomic.
- Publishing goes through an `arc_swap::ArcSwap<Document>` that the render and
  audio threads read **without locks**.
- Commands are plain data (`serde`), which also enables a debug "command log"
  replay for bug reports.

## 4. Render-graph design (`voxy-render`)

### 4.1 Pipeline

```
Arc<Document>, CompId, Time, RenderSettings
        │
        ▼  evaluate()            (voxy-core, pure, CPU, deterministic)
   EvaluatedComp                 every property resolved at `time`; world transforms
        │                        via parenting; visibility/in-out culled
        ▼  build_graph()         (voxy-render, CPU)
   RenderGraph (DAG)             nodes + edges + per-node content hash + ROD/ROI
        │
        ▼  schedule()            topological order, texture-lifetime analysis,
        │                        cache lookups prune whole subtrees
        ▼  execute()             (GPU via wgpu; CPU nodes for OFX & decode upload)
   Rgba16Float linear premultiplied target
        │
        ├─▶ DisplayTransform node → swapchain texture (preview)
        └─▶ OutputTransform node  → readback (RGBA8/16 or YUV planes) → encoder (export)
```

Preview and export run **the same `evaluate → build_graph → execute`**.
`RenderSettings { resolution_scale, quality }` is the only difference: preview
can render at ½ or ¼ resolution, and export always renders at full. A
full-quality preview frame is bit-identical to the matching export frame
before encoding.

### 4.2 Node types

| Node | Inputs | Notes |
|---|---|---|
| `Solid`, `Gradient` | — | generated in shader |
| `MediaFrame` | — | decoded frame upload; source-time computed in `evaluate` |
| `VectorRaster` | — | shapes/masks/text → coverage+color via vector backend |
| `Effect` | 1..n | built-in WGSL effect, or `OfxEffect` (CPU readback/upload or GPU suite) |
| `Mask` | layer, mask coverage | mask modes combine coverage before apply |
| `Matte` | layer, matte source | alpha/luma (inverted) |
| `Transform` | 1 | 2D affine, filtered sampling (bilinear/bicubic per quality) |
| `Composite` | below, layer | blend mode + opacity, Porter-Duff over |
| `Precomp` | — | recursively builds a sub-graph at remapped time |
| `Adjustment` | accumulated-below | applies effect chain to everything below, then composites with layer's mask/opacity |
| `DisplayTransform` / `OutputTransform` | 1 | linear → sRGB/Rec.709 (+dither for 8-bit) |

Each layer goes through: source → masks → effects → matte → transform →
composite onto the accumulated stack. Mask and effect order are configurable
where AM differs (to be confirmed from samples).

### 4.3 Regions, caching and determinism
- **ROD/ROI:** every node reports its region of definition. Requests propagate
  regions of interest backwards, so off-canvas blur sources and OFX
  `GetRegionsOfInterest` work in one consistent model.
- **Content hash:** `hash(node kind, resolved params, input hashes, source
  frame identity)`. Static layers hash the same across frames, so a 10-second
  static title renders once.
  - A RAM LRU of final frames (budget in bytes) feeds scrubbing and playback.
  - A GPU-resident pool caches intermediates.
  - A disk cache comes later (M9).
- **Background rendering:** a render thread works ahead of the playhead and in
  both directions around it while idle.
- **Determinism rules:**
  - Fixed evaluation and dispatch order.
  - No atomics-order-dependent reductions in shaders; blur and reduction use
    fixed tile orders.
  - Any randomness (noise, grain) is seeded by `(effect id, frame)`.
  - No wall-clock or thread-timing inputs.
  - Decoders run in exact-seek mode.
  - The guarantee holds on **the same machine, driver and wgpu backend**.
    Across GPUs we target perceptual equality: SSIM ≥ 0.999, as checked by the
    golden tests. Bit-exact output across vendors would need a CPU renderer
    (see question Q4).

### 4.4 Color
- The working buffers are `Rgba16Float`, linear-light, with premultiplied
  alpha. Inputs are linearized on upload according to their tagged transfer
  function: sRGB, Rec.709, or later PQ/HLG.
- **Fidelity concern with Alight Motion:** mobile compositors usually blend,
  blur and fade in **gamma-encoded (sRGB) space**, not linear. If AM does that,
  a strictly linear pipeline will make AM projects look different at
  semi-transparent edges, in blend modes and in blurs.
  - Proposal: a per-project `working_space: Linear | SrgbCompat` setting. Both
    use the same float buffers, and only the encode/decode around blend and
    effect nodes changes.
  - New voXY projects default to Linear.
  - AM imports default to whichever space the golden tests show matches. I'll
    measure it against your reference renders instead of assuming.

## 5. Threads and data flow

| Thread | Owns | Talks via |
|---|---|---|
| UI (main) | eframe/egui, `History` | sends `RenderRequest`, reads results; publishes `Arc<Document>` through `ArcSwap` |
| Render | wgpu queue submissions, graph, frame cache | `crossbeam-channel` requests in, `FrameReady` out (texture handle) |
| Decode pool | one FFmpeg context per open media | bounded prefetch ring per source; seek requests |
| Audio | cpal callback | `rtrb` lock-free SPSC ring; never allocates or locks |
| OFX sandbox(es) | plugin processes | shared memory + IPC (§6) |

The audio clock is the master clock during playback. Video frames are chosen
against it, and late frames are dropped in preview, never in export. The hot
path takes no locks: the document reaches other threads as an immutable `Arc`
snapshot, and everything else moves through channels.

## 6. OpenFX host (summary; detail in M7/M8)

- **Discovery:** scan the standard paths and user paths, walk the
  `.ofx.bundle/Contents/<arch>/` layout (`Win64`, `Linux-x86-64`,
  `MacOS`/`MacOS-x86-64`/`MacOS-arm-64`), and keep a cache keyed by bundle
  path, mtime and size.
- **Out-of-process proposal:**
  - `voxy-ofx-sandbox` loads one bundle per process with `libloading` and
    implements the suites against a local mirror of the instance state.
  - Image buffers travel through **shared memory**: a pool of named mappings
    via `shared_memory`/`memmap2`.
  - Control messages travel over **local IPC**: named pipes on Windows, Unix
    domain sockets elsewhere, via `interprocess`, with `postcard`-encoded
    messages.
  - Each render request carries a snapshot of every parameter value at the
    render time, plus the times the plugin is known to sample. A
    `paramGetValueAtTime` for any other time costs one round trip, which is
    rare in practice.
  - Watchdog: per-action timeouts. If the process crashes or hangs, it is
    killed and the plugin is marked failed for the session. Three failures put
    it on a persistent blocklist, and the UI shows a clear message. voXY
    itself never dies with the plugin.
- **Images:** CPU float and 8/16-bit RGBA first, using GPU readback and upload
  around the node. OpenGL and other GPU-render suites come in M8, and they
  require in-sandbox GL contexts with readback (wgpu↔GL sharing across
  processes isn't portable).
- **Parameter mapping:** every OFX param becomes a `PropertyDesc` keyed
  `ofx:<pluginId>/<paramName>`, so plugins keyframe and appear in the graph
  editor like built-ins.
- **Testing:** the conformance harness runs against the OpenFX Support sample
  plugins and the Natron `openfx-misc` set, both built in CI.

## 7. Alight Motion compatibility (`voxy-am-compat`)

**I will not write any schema until your samples arrive.** Only the
architecture is proposed here.

1. **Lossless XML layer first.** A small DOM built on `quick-xml`'s reader:
   - It preserves element order, attribute order, namespaces, text and
     whitespace, comments and the XML declaration.
   - Writing an untouched DOM reproduces the input byte-for-byte. That's the
     round-trip baseline, and fuzzing enforces it.
2. **Typed views on top.** Typed structs are extracted from the DOM. Each one
   keeps a back-reference (`NodePath`) and an `extra` list of unrecognized
   attributes and child elements.
   - On export, edited fields are written back into the original DOM node.
     Nodes voXY creates are written from the typed model, with attribute order
     following the conventions observed in the samples.
   - This is a deliberate refinement of "quick-xml + serde": derived serde XML
     deserialization drops unknown content and reorders fields, which would
     break the lossless requirement. `serde` is still used for the TOML
     mapping tables.
3. **The native model carries foreign data:** `ForeignData { am:
   Option<AmNodeRef> }` on layers, comps, effects and properties. A voXY →
   AM export therefore merges into the preserved originals instead of
   regenerating them.
4. **Mapping tables:** `mappings/am/*.toml`, one per area as listed in the
   brief. `cargo xtask am-coverage` generates `docs/am-effect-coverage.md`
   from them.
5. **Import report:** a structured `ImportReport { mapped, approximated,
   preserved_unrendered, missing_media, warnings }`, shown in a dialog after
   every import.
6. **Version gate:** read the version fields. A newer-than-known version gets a
   warning and opens **read-only for export to AM**, so voXY never writes a
   format it doesn't understand.
7. **Tests:**
   - DOM byte round-trip.
   - Typed round-trip (import → export → import gives an equal model).
   - `cargo-fuzz` targets for the zip, DOM and typed layers.
   - Golden SSIM/PSNR tests against your reference videos, with per-sample
     scores written to a report.

## 8. Native project format (`.voxy`)
- `.voxy` is a **single UTF-8 JSON file** with a top-level `format_version`
  (semver).
  - The schema is generated with `schemars` and published under
    `docs/voxy-format/`.
  - Assets live in a sibling `<name>.assets/` folder and are referenced by
    relative paths plus a content hash (BLAKE3) for relinking.
- "Collect & package" writes a `.voxyz` zip for sharing.
- Loaders migrate older versions forward step by step. Newer versions are
  refused with a clear message.
- **Autosave:** every N seconds after an edit, written to
  `<name>.voxy.autosave` atomically (write to a temp file, fsync, rename).
  - On startup, an autosave newer than the project file triggers a recovery
    prompt.
  - Crash recovery also checks a small session lock file.
- **`.voxypreset`:** the same JSON schema with a `Preset` root (layers or
  effect stacks plus metadata, tags and thumbnail).

## 9. Decisions needed from you

**Q1 — UI toolkit. Recommendation: `egui` via `eframe` (wgpu backend), with
`egui_dock` for docking.**
- The editor is mostly custom-painted widgets: timeline, keyframe lanes, graph
  editor, waveforms and gizmos. Immediate mode makes these direct to write and
  keeps them in sync with a document that changes every frame.
- `eframe`'s wgpu backend lets the viewport display the compositor's texture
  **with no copy**, on the same `wgpu::Device`.
- `egui_dock` provides dockable, resizable tabbed panels today.
- Against it: egui's default look needs real styling work for a polished
  product, and complex text editing in panels is basic. Layer text is rendered
  by our own pipeline, so this only affects UI chrome.
- `iced`'s Elm architecture is cleaner for forms but heavier for
  high-frequency custom canvases, and its docking story is weaker.

**Q2 — Vector backend. Recommendation: `vello` (GPU compute), with `kurbo`
for geometry, `parley` for text layout, and `i_overlay` for boolean ops.**
- Motion graphics re-tessellate animated paths every frame. `lyon` would do
  that on the CPU per frame, then render with MSAA. Vello rasterizes on the GPU
  with analytic anti-aliasing and handles fills, strokes, dashes, gradients,
  clips and blend layers natively.
- Text glyph outlines from `parley`/`skrifa` go through the same path, so text
  and shapes match exactly.
- `vello_cpu` gives a CPU reference rasterizer for golden tests.
- Risks:
  1. Vello is pre-1.0 and pins a specific `wgpu` version, so it must line up
     with eframe's. I'll pin a matched pair.
  2. It needs compute shaders, so there's no WebGL2-class fallback, which is
     acceptable for a desktop app.
- Alternative: `lyon` is mature and stable, but its AA quality is lower and the
  CPU cost of animated paths is higher.

**Q3 — OFX sandbox. Recommendation: out-of-process from the first OFX
milestone (M7), one sandbox process per plugin bundle, with shared-memory
images and pipe/socket IPC (§6).**
- An in-process "catch the crash" approach isn't sound. Plugin crashes are
  usually memory corruption (SIGSEGV or SEH) that leaves the process state
  unknown, and unwinding across `extern "C"` is undefined behaviour.
- I'd keep an `--ofx-in-process` debug flag for plugin developers.
- Cost: about one extra copy per OFX node through shared memory, and a more
  complex param-suite implementation.

**Q4 — Determinism scope.** Accept "bit-identical on the same machine and
driver; SSIM-equivalent across GPUs"? Or must output be bit-identical across
machines? The second would force a CPU renderer for export and roughly
5–20× slower exports.

**Q5 — H.264/H.265 encoding under an LGPL FFmpeg.** `libx264` and `libx265`
are **GPL**, so an LGPL build can't include them. Proposal:
- H.264 via platform hardware encoders (NVENC, QSV, AMF, VideoToolbox, Media
  Foundation) with **OpenH264** (BSD) as the software fallback.
- H.265 via hardware encoders, with **kvazaar** (BSD-3) as the software
  fallback where available.
- Users who supply their own GPL FFmpeg get x264 and x265 automatically,
  because the library is loaded dynamically.
- H.264/HEVC patent licensing is a business question for distribution, so I'm
  flagging it for you rather than deciding it.
- For GIF: FFmpeg `palettegen`/`paletteuse`. I'll avoid `gifski` (AGPL) and
  `imagequant` (GPL).

**Q6 — Project file.**
- JSON or RON? I recommend **JSON**: universal tooling, and a schema can be
  generated for it.
- A single file plus a sibling `.assets/` folder, or a zip container? I
  recommend the **single file plus folder**, which is diffable and
  git-friendly, with `.voxyz` for packaging.

**Q7 — Minimum toolchain and platforms.**
- I propose Rust edition 2024 with MSRV pinned to the current stable at M1.

## Implementation notes (Milestone 1)

These are refinements made while building Milestone 1. They are consistent
with the approved design.

- **Property serialization.** Property descriptors are referenced by `key` in
  files and are not duplicated.
  - Unknown keys load with a generic descriptor and are written back
    unchanged.
  - Values are validated when edited: type, finiteness and range clamping.
  - Values are not re-clamped when loaded, so a load/save cycle never alters
    data.
- **Undo history.**
  - `History` stores whole-document snapshots, with copy-on-write sharing.
  - Edits that leave the document unchanged record no step.
  - The undo limit is a step count (1000). The proposal's approximate byte
    budget is deferred until real projects show it is needed.
- **Render "graph".** In Milestone 1 the graph is a single chain: clear, one
  composite per layer, then the output transform. It is built as a pure,
  GPU-free `RenderPlan`. The DAG with content hashes arrives with effects and
  masks.
- **Images.** Images are decoded to sRGB8, then a GPU "prepare" pass converts
  them once into premultiplied RGBA16F encoded for the working space. That
  keeps bilinear filtering free of fringes and gives both working spaces one
  code path.
- **Edge antialiasing.** Layer quads are not antialiased yet; edges are
  aliased. Analytic coverage antialiasing for layer edges, and vello for
  shapes, come in later milestones.
- **Threads.** Milestone 1 renders on the UI thread, and only when the
  document revision or viewport size changes. The dedicated render, decode and
  audio threads arrive with playback in Milestone 3.
- **voXY's own license.** It has not been chosen. That is the owner's
  decision; see LICENSING.md.

## Implementation notes (Milestone 2a: keyframe model)

- **Ease handles live on the keys.** A segment's curve is the CSS-style
  normalized cubic `(0,0)`, `k0.ease_out`, `k1.ease_in`, `(1,1)`.
  - `x` is restricted to `[0, 1]`, so time maps to one value; `y` may
    overshoot.
  - Linear sides use the exact-linear handles (1/3, 1/3) and (2/3, 2/3).
  - Speed/influence conventions from other tools (and Alight Motion's,
    once known from samples) convert to this form in the mapping tables.
- **One ease curve per key, shared by every dimension.** Separate-dimension
  animation (independent X/Y curves) can be added later as split
  properties, without changing this model.
- **Solving.** Bézier x is inverted with Newton plus a fixed-length
  bisection fallback. Arc length uses 32 spans of 5-point Gauss–Legendre
  quadrature, inverted with safeguarded Newton. All iteration limits are
  fixed, so evaluation is deterministic, and it is pure, recomputed per
  call. Caching comes with the frame cache (Milestone 9) if profiling asks
  for it.
- **Overshoot on motion paths** continues in a straight line along the end
  tangent. Interpolated values are clamped to the property's hard range.
- **Color keys interpolate in linear light, straight alpha.** Whether
  Alight Motion interpolates in sRGB will be settled by the golden tests,
  not assumed.
- **Keys are identified by time.** There are no key IDs. Commands address
  keys by their current time, and drags merge into one undo step.
- **Editing an animated property** at the current time creates or updates
  the key there, as in common motion-design tools.
- **Format 0.2.0** adds keyframed properties. 0.1.0 files load unchanged.
